## Application Security

Application-layer protection centers on strong account authentication and abuse-prevention at the API level.

### Two-Factor Authentication (2FA)

- **Requirement:** 2FA is **mandatory for all users** not opt-in, and not limited to admin accounts.
- **Factors Combined:**
  - **Email + password** , checked against a **bcrypt** hash (industry-standard, salted, adaptive hashing — passwords are never stored in plaintext or reversibly encrypted).
  - A **Time-based One-Time Password (TOTP)** code, generated by an authenticator app (Google Authenticator, Authy, etc.), set up via a scanned QR code during enrollment.
- **TOTP Secret Storage:** TOTP secrets are encrypted at rest (via Fernet symmetric encryption) before being stored in Redis, and only decrypted in-memory at verification time.
- **Login Flow:** Login is a two-step handshake - a successful password check returns a short-lived MFA challenge token (valid 10 minutes), which must then be exchanged for a full access token by submitting a valid TOTP code. A password alone never grants API access.
- **Account Lockout:** After 3 failed login attempts, the account is locked for 15 minutes, independent of rate limiting below - this blocks slow, distributed guessing attempts that stay under the rate-limit threshold.
- **Why this matters:** Requiring both factors means a leaked or guessed password alone isn't enough to compromise an account - the attacker would also need the user's TOTP device.

### Rate Limiting

- **Implementation:** Rate limiting is enforced at the endpoint level, keyed by client IP (or by user ID for TOTP verification).
- **Applied limits:**
  - `POST /auth/login` - 5 requests/minute per IP
  - `POST /auth/totp/setup`, `/auth/totp/enable`, `/auth/totp/verify` - 10 requests/minute per IP, **plus** a secondary per-user limit of 8 verification attempts per 5 minutes
  - `POST /auth/forgot-password` - 5 requests per 15 minutes per IP
- **Primary Targets:** These endpoints are the classic targets for credential stuffing, brute-force, and TOTP-guessing attempts - rate limiting is applied specifically where password or code guessing could otherwise be automated.

### Input Validation

All request bodies are validated through **Pydantic schemas** (FastAPI's request-validation layer) before reaching business logic - malformed types, missing required fields, and out-of-range values are rejected automatically at the API boundary. Custom field-level validators (e.g. for device attributes) are defined separately from the general schema types.

### AI Pipeline Security

The Raspberry Pi edge devices send **classification results** (not raw images) to the backend, which reduces the attack surface compared to transmitting and storing raw camera footage. The Pi does not use a separate device credential - it authenticates as a regular recycling-center user account (same JWT-based login as a human operator), so classification submissions go through the same access-token and role-check path as any other API request.
